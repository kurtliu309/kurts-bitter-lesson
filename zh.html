Kurt's Bitter Lesson

一个人、两家模型、六版派发规则：我们怎样把一条精巧的流水线，砍回一个脚本加一句“能交出去就交出去”。

Kurt × Claude（Opus / Haiku）× DeepSeek（Flash / Pro）· 数据截止 2026-11-12
摘要1 背景2 六轮迭代3 实验4 被忘了三次的事5 结论6 局限附录

摘要。我们想让贵的模型（Claude Opus）少干活、便宜的模型（DeepSeek）多干活。为此在一天之内把派发规则 delegate-coding 从 0.3 改到 2.1，先后加过额度切档、代码摘要、规格写手、初审、终审、闸门、账本、副本隔离、多轮返工，又几乎全部删掉。实测显示：机器检查越多，检查之间互相打架的失败点越多；真正有用的只有三样东西——给执行者完整的工具、一条硬性的轮数上限、一次由强模型做的独立检查。最终版本的代码量是峰值的 14%，而它第一次就把 1.0 卡死的那道题做完了。另外，有一条关键事实（--bare 会让子代理消失）我们写下来过两次，还是在第三次又踩了一遍。

核心思想。不要想太多架构。对强模型来说，架构很可能是妨碍；流程设计在纸上再合理，也很可能是未经验证的空想。

1背景：一个很朴素的问题

Kurt 用 Claude Code 桌面版做工程。Opus 质量好但额度有限；DeepSeek 通过 Anthropic 兼容接口也能驱动同一个 Claude Code 命令行，几乎不占 Claude 额度。于是问题变成：主对话里的 Claude 应该把哪些活交给 DeepSeek，怎么交，交完怎么验收？

答案写在一个 skill 文件里（delegate-coding/SKILL.md），每次涉及工程的对话开始前必须加载。这篇报告记录这个文件的六次大改，以及支撑每次改动的实测。

4被忘了三次的事

这篇报告最该被记住的部分不是哪张图，而是这条时间线。

11-09 · 探针
显式允许 7 个工具（含 Agent），DeepSeek 只看到 Bash、Edit、Read 三个。报告写了“7 个只看到 3 个”，没解释。
11-12 上午 · T0
查清原因：--bare 模式只给三个工具，还会把 CLAUDE_CODE_SIMPLE=1 传给下一层。去掉 --bare 后子代理能拉起，也确实跑在 DeepSeek 上。写进了两份笔记。
11-12 中午 · 2.0.0
大简化时，新脚本又写回了 --bare，SKILL.md 里还认真记了一句“拉不起子代理”——把一个可修的限制当成了既定事实。笔记里甚至写着“普通任务继续用 --bare”。
11-12 下午 · 2.1.0 第 1、2 次尝试
Kurt 问“为什么还不能拉子代理”。先把 Agent 加进允许名单——没用；再用 --tools 显式列工具——还是没用，连 Glob、Grep 都没有。
11-12 下午 · 2.1.0
去掉 --bare，改用独立配置目录 + --strict-mcp-config 隔离。子代理成功；顺手发现只读模式其实拦不住写文件（acceptEdits 会自动放行），一并修掉。

答案在 T0 里已经有了，笔记也写了两份。可是做 2.0.0 的那一轮对话没有去读它，新脚本是照着旧脚本改的，旧脚本里就带着 --bare。写下来的经验只在有人读的时候才算数；真正能保住它的，是写进会被执行的东西里——所以 2.1.0 把原因写成了脚本里紧挨着那一行的注释。

5结论：Kurt's Bitter Lesson

不要想太多架构。它很可能在妨碍强模型；你设计的流程，也很可能是没人验证过的空想。

Rich Sutton 的 The Bitter Lesson 说，长期看，依靠通用计算的方法总会赢过人手编进去的领域知识。我们在一个小得多的尺度上，花一天时间把这件事亲身走了一遍。归结起来是两个论点。

论点一

架构在妨碍强模型

我们每加一层，都在收窄强模型能看到、能做的东西。

  • 路线 B 里，Opus 写规格看的是 Flash 写的摘要，不是代码——架构让最强的模型用最弱的模型的视角干活。
  • 闸门和验收命令互相矛盾，能干的执行者怎么做都过不了（图 5）。
  • 为了“隔离”用的 --bare，悄悄拿走了子代理——恰恰是让模型自己组织工作的那项能力（图 6）。
  • 传话层让 Haiku 去猜意图，而不是直接回答。
  • 真正抓到 bug 的，是结构的反面：一个强模型自由地读 diff（图 2）。
论点二

流程设计常常是未经验证的空想

我们搭的大部分东西，理由是推理，而不是它真的挡住过哪次失败。

  • V2 有一份 37 项的设计清单，只有少数几项在 T0–T6 实验里碰到过。
  • 额度 80% / 70% 的切档阈值是拍的，没验证过。
  • 闸门在真实派单里的拦截率从没测过——在测之前就删了。
  • 30 条单元测试证明的是机制能跑，不是机制有用；真跑第一单就失败。
  • “谁写规格”的分档决定只基于一道题。

那该怎么做

  1. 从最简单的开始：把任务和完整的工具交给模型。
  2. 加一条由脚本强制的硬上限（轮数），而不是一条要模型记住的规则。
  3. 真跑一单。只有当一次真实失败本可以被某个机制挡住时，才加这个机制——并且测量它。
  4. 保留一次强模型的独立检查；其余的，等数据说话再加。

支撑两个论点的七条观察

    6局限

    • 样本很小：T4 只有一道题，T5 是 3 道题各 2 次，T6 没有打分。任何“Flash 比 Pro 好”“Opus 写规格更省”的说法都只是暂定。
    • 所有实验都在一台 Windows 机器、同一天、同一个人身上完成；没测并发、长任务和超时看门狗。
    • 额度百分比只有整数，单次 Opus 调用的成本看不出来，所以“省了多少 Claude 额度”没有可靠数字。
    • 闸门在真实派单里的拦截率和误拦率从没测过——在测之前它就被删了。
    • 2.1.0 去掉 --bare 后，DeepSeek 会读到项目自己的 CLAUDE.md / AGENTS.md；这被当成好事，但长期影响没观察。
